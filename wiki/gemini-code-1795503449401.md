# 04. 線性流程（DAG）vs. 狀態迴圈（StateGraph）

## 1. 為什麼不能只用線性流程？
傳統的資料處理管線多為 **有向無環圖（DAG, Directed Acyclic Graph）**，資料從步驟 A 流向 B 再流向 C，單向執行到底。然而在 AI 生成任務中，LLM 具有機率不確定性，一旦步驟 B 產出品質不佳，線性流程無法回頭修正，導致最終成果失敗。

## 2. 狀態圖（StateGraph）與條件迴圈（Loop）
為了實現 Reflection 模式，現代 Agent 框架（如 LangGraph）引入了 **StateGraph** 概念：
- **共享狀態（State）**：一個貫穿整個流程的資料結構（字典或 JSON），用來儲存「目前草稿內容」、「Wiki 來源」、「檢查結果狀態（PASS/FAIL）」與「修改建議清單」。
- **條件邊（Conditional Edge）**：在檢查節點後方設置分岔路。若狀態為 `FAIL`，流程沿著迴圈邊退回「生成節點」；若狀態為 `PASS`，則放行進入「輸出節點」。

## 3. 迴圈設計的三大安全原則
1. **設定最大迭代次數（`max_iterations`）**：必須設定重試上限（例如最多 3 次），防止模型因標準過高而陷入無窮迴圈（Infinite Loop），耗盡 Token 額度。
2. **明確的結構化回饋**：審查節點不能只說「寫得不好」，必須輸出具體錯誤原因（如「第 3 頁超過 120 字」），生成節點才能精準修正。
3. **檢查前置原則（Shift-Left Testing）**：將檢查節點盡量往前移到輕量級的文字資料階段，避免在最後生成繁重的 HTML/程式碼後才重跑整條管線。
